## Chapter 106: Quality Data Architecture and the Tool-Choice Matrix
### The engineering question

*Which tool is the right one for this decision?*

Not *"how do I do the same thing in five different software packages."* This is the most important pedagogical shift in this part of the manual. Knowing how to reproduce a histogram in Excel, Minitab, Python, R and Power BI is not a competency; knowing which of the five should produce the number that goes into a PPAP report is.

**The rule that summarizes the matrix:**

> **The visualization tool is not the inference tool.**

Power BI and Excel are excellent at showing. R, Python and Minitab are the tools for deciding. SQL is the tool for fetching. Confusing these roles produces two frequent pathologies: pretty dashboards with wrong statistics, and correct analyses that nobody sees.

### Important correction: Power BI does **not** replace SPC

A common claim — one this manual explicitly corrects — is that Power BI "replaces many static control charts."

**The correct statement:**

> **Power BI can act as an SPC monitoring and visualization layer, but it does not replace the statistical method or specialized software for every application.**

What Power BI does well for SPC:

- showing the updated chart in near-real time;
- distributing access to whoever needs it, without installing software;
- drilling down by shift, line, part number, operator;
- triggering automatic alerts.

What Power BI does **not** do, or does poorly:

- correctly estimating $\hat{\sigma}_{within}$ from subgroups (which requires $d_2$, $c_4$ and rational-subgroup logic);
- applying the Nelson rules with the correct semantics;
- computing capability for non-normal distributions;
- Gage R&R, ANOVA, DOE, residual diagnostics;
- testing assumptions.

**The correct architecture is layered, not a replacement:**

```
ERP / MES / Sensors / LIMS
          ↓
     SQL / Data Lake            <- data layer
          ↓
   Power Query / dbt / Python   <- transformation layer (ETL/ELT)
          ↓
   R / Python / Minitab         <- STATISTICAL layer (this is where decisions are made)
          ↓
   Power BI / Excel             <- VISUALIZATION and distribution layer
          ↓
   Control Plan / Action        <- documented DECISION layer
```

The most common architectural mistake is connecting the first layer directly to the second-to-last one and computing statistics inside the visualization tool.

### Quality data sources

| System | What it contains | Typical pitfall |
|---|---|---|
| **ERP** | Orders, lots, suppliers, costs, nonconformances | Dates are recording dates, not occurrence dates |
| **MES** | Production, times, downtime, traceability | Granularity changes between lines |
| **LIMS** | Lab results | Detection limits recorded as zero |
| **CMM / metrology** | Dimensional measurements | Local files, no centralized history |
| **Sensors / IoT** | Process time series | High frequency, strong autocorrelation, sensor failures |
| **CRM / customer service** | Complaints, warranty | Free text, no consistent taxonomy |

> **Joining these sources is where most of the value lives — and where most of the errors live.** A part has one number in MES, another in ERP, and another on the customer's label. Without a reliable traceability key, correlating complaints with process parameters is impossible.

This is why **traceability** is simultaneously an IATF 16949 requirement and the technical condition that makes quality analytics possible at all.
