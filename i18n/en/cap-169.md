## Chapter 169: Classification Metrics Under Class Imbalance and Economic Decision Thresholds

<h3 id="the-engineering-question">The engineering question</h3>
<p><em>The model that classifies lots as “conforming” or “rejection risk” is right 96% of the time. Should it be approved for production use?</em></p>
<p>That depends entirely on a question accuracy alone can’t answer: how many real risk lots were in the sample? In <a href="#/aula/cap-111">Chapter 111</a> we already saw that, under class imbalance, a trivial model that always answers “conforming” can have very high accuracy and zero recall. This chapter goes deeper: how to choose the right metric when the class of interest is rare — in the reference manufacturing project, quality-compromised lots make up between 5% and 40% of cases, depending on the process — and how to turn a predicted probability into a decision (approve/hold the lot) using the real cost of being wrong in each direction.</p>
<h3 id="why-accuracy-is-misleading-under-class-imbalance">Why accuracy is misleading under class imbalance</h3>
<p>The confusion matrix is the starting point for any classification metric. From it, three metrics answer different questions:</p>
<p><div class="math-block" data-math="\text{Precision} = \frac{TP}{TP + FP} \qquad \text{Recall} = \frac{TP}{TP + FN} \qquad F_1 = \frac{2 \times \text{Precision} \times \text{Recall}}{\text{Precision} + \text{Recall}}"></div></p>
<p><strong>Precision</strong> answers “of the lots the model flagged as risk, how many really were?” — it matters when a false alarm is expensive (extra inspection, a lot held unnecessarily). <strong>Recall</strong> answers “of the lots that really were at risk, how many did the model catch?” — it matters when letting a defect through costs more than investigating a false alarm. <strong>Accuracy</strong> blends both classes into a single frequency-weighted average — and with a rare class, that average is dominated by the majority class, hiding exactly the performance that matters.</p>
<h3 id="pr-auc-vs-roc-auc-which-to-choose">PR-AUC vs. ROC-AUC: which to choose under class imbalance</h3>
<p>The ROC curve (Recall vs. False Positive Rate) is the more common one, but it has a blind spot: the False Positive Rate uses the total number of negatives as its denominator — and when negatives are the overwhelming majority, that rate stays low even with many false positives in absolute terms. The Precision-Recall (PR) curve doesn’t use true negatives in either axis, which makes it more sensitive to the rare class and, for that reason, the recommended reference when the positive class is a minority and the cost of a false positive matters. The area under the PR curve (PR-AUC) is the scalar summary of that curve, the same way AUC summarizes ROC.</p>
<p><strong>Rule of thumb:</strong> with moderate-to-severe imbalance (positive class below ~20%), report PR-AUC as the primary metric for comparing models, and Precision/Recall/F1 at a specific threshold as operational metrics.</p>
<h3 id="class-weight-balanced-how-scikit-learn-compensates-for-the-rare-class"><code>class_weight=“balanced”</code>: how scikit-learn compensates for the rare class</h3>
<p>Instead of resampling the data (over- or under-sampling), many scikit-learn models accept a per-class weight that changes the loss function directly: errors on the rare class cost more during training. With <code>class_weight=“balanced”</code>, each class’s weight is computed as:</p>
<p><div class="math-block" data-math="w_c = \frac{n_{\text{samples}}}{n_{\text{classes}} \times n_c}"></div></p>
<p>where <span class="math-inline" data-math="n_c"></span> is the number of examples of class <span class="math-inline" data-math="c"></span> in the training set. The rarer the class, the larger the weight — the practical effect is to push the model to stop ignoring the minority class just because it contributes little to the average loss. This changes how the model is trained; it does not replace choosing a decision threshold, which is a separate decision, made after the model is trained (see next section).</p>
<h3 id="worked-example-classifying-risk-lots">Worked example: classifying risk lots with a rare class</h3>

import pandas as pd
from sklearn.linear_model import LogisticRegression
from sklearn.metrics import (precision_recall_curve, average_precision_score,
                              roc_auc_score, f1_score, precision_score, recall_score)

rng = np.random.default_rng(2026)
n = 4000

# --- Simulation: 3 process variables + 1 rare "risk lot" class ---
temp = rng.normal(215, 7, n)
pressao = rng.normal(4.2, 0.3, n)
desgaste_ferramenta = rng.uniform(0, 100, n)

risco = -3.6 + 0.05 * (temp - 215) + 1.6 * (pressao - 4.2) + 0.03 * desgaste_ferramenta
p_defeito = 1 / (1 + np.exp(-risco))
y = rng.binomial(1, p_defeito)

X = pd.DataFrame({"temp": temp, "pressao": pressao, "desgaste": desgaste_ferramenta})
print(f"Risk-lot rate in the sample: {y.mean():.1%}  (MINORITY class)\n")

corte = int(0.7 * n)
X_tr, X_te = X.iloc[:corte], X.iloc[corte:]
y_tr, y_te = y[:corte], y[corte:]

# --- Two models: without and with class balancing ---
m_simples = LogisticRegression(max_iter=1000).fit(X_tr, y_tr)
m_balanceado = LogisticRegression(max_iter=1000, class_weight="balanced").fit(X_tr, y_tr)

for nome, m in [("Without class_weight", m_simples), ("With class_weight=balanced", m_balanceado)]:
    p = m.predict_proba(X_te)[:, 1]
    y_hat_05 = (p &gt;= 0.5).astype(int)
    print(f"{nome}:")
    print(f"  Accuracy at 0.5      = {(y_hat_05 == y_te).mean():.3f}")
    print(f"  Precision at 0.5     = {precision_score(y_te, y_hat_05, zero_division=0):.3f}")
    print(f"  Recall at 0.5        = {recall_score(y_te, y_hat_05, zero_division=0):.3f}")
    print(f"  F1 at 0.5            = {f1_score(y_te, y_hat_05, zero_division=0):.3f}")
    print(f"  ROC-AUC              = {roc_auc_score(y_te, p):.3f}")
    print(f"  PR-AUC               = {average_precision_score(y_te, p):.3f}\n")

# --- Optimal threshold under asymmetric economic cost ---
custo_fn = 480.0   # risk lot released -- cost of a customer complaint/rework
custo_fp = 35.0    # good lot held for unnecessary extra inspection

p_te = m_balanceado.predict_proba(X_te)[:, 1]
limiares = np.linspace(0.02, 0.90, 45)
resultados = []
for lim in limiares:
    y_hat = (p_te &gt;= lim).astype(int)
    fn = int(((y_hat == 0) &amp; (y_te == 1)).sum())
    fp = int(((y_hat == 1) &amp; (y_te == 0)).sum())
    custo = fn * custo_fn + fp * custo_fp
    resultados.append({"threshold": round(lim, 3), "FN": fn, "FP": fp, "total_cost": custo})

tab = pd.DataFrame(resultados)
otimo = tab.loc[tab["total_cost"].idxmin()]
print("Threshold sweep (every 5th point):")
print(tab.iloc[::5].to_string(index=False))
print(f"\nThreshold that minimizes expected cost: {otimo['threshold']:.3f}")
print(f"  (well below 0.5 -- because cost_FN/cost_FP = {custo_fn/custo_fp:.1f}x, "
      f"it pays to accept more false alarms to avoid an escape)")</code></pre></div></div></div><p><strong>Engineering reading.</strong> Note that <code>class_weight=“balanced”</code> improves recall at 0.5, but the real gain comes from combining it with the threshold sweep: the economic cost defined by the business (not the statistical convenience of 0.5) is the criterion that decides where to cut. This threshold-by-cost reasoning was already introduced as a concept in <a href="#/aula/cap-138">Chapter 138</a> (model validation and decision threshold); here it gets the full treatment, with asymmetric false-positive and false-negative cost.</p>
<h3 id="the-optimal-threshold-is-an-economic-decision-not-a-fixed-number">The optimal threshold is an economic decision, not a fixed number</h3>
<p>The 0.5 threshold is a library convention, not a statistical truth. The general rule is:</p>
<p><div class="math-block" data-math="\text{Total cost}(\text{threshold}) = FN(\text{threshold}) \times \text{cost}_{FN} + FP(\text{threshold}) \times \text{cost}_{FP}"></div></p>
<p>and the optimal threshold is the one that minimizes this function — always computed on the <strong>validation</strong> set, never on the test set, for the same methodological reason that already applies to hyperparameter choice: if the threshold is tuned by looking at the test set, the test set stops measuring generalization. The next chapter formalizes exactly that separation between fitting data and final evaluation data, in an even trickier setting: production data ordered in time.</p>

<h3 id="common-mistakes">Common mistakes</h3>
<ol>
<li><strong>Reporting accuracy as the sole metric under class imbalance.</strong> A trivial “always conforming” classifier can have 95% accuracy and zero recall.</li>
<li><strong>Comparing models by ROC-AUC when the positive class is very rare.</strong> PR-AUC is more sensitive to the minority class in that regime.</li>
<li><strong>Using <code>class_weight=“balanced”</code> as a substitute for choosing a threshold.</strong> These are two independent decisions: one changes how the model is trained, the other changes how the predicted probability becomes a decision.</li>
<li><strong>Choosing the threshold by looking at the test set.</strong> That contaminates the final performance estimate — the threshold should be chosen on validation.</li>
<li><strong>Assuming false-positive and false-negative costs are equal by default.</strong> They rarely are, and the gap is often a full order of magnitude in industrial quality contexts.</li>
</ol>
