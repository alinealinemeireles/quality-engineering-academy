## Chapter 170: Temporal Cross-Validation and Hyperparameter Search (TimeSeriesSplit, GridSearchCV)

<h3 id="the-engineering-question">The engineering question</h3>
<p><em>Your model had 91% accuracy in standard cross-validation. A month later, in production, it dropped to 64%. What happened?</em></p>
<p>Almost always, the answer is: the cross-validation scheme didn’t respect the order of time. We already saw in <a href="#/aula/cap-169">Chapter 169</a> how to pick the right metric to judge a quality model; this chapter deals with an earlier, more fundamental question — how to produce a performance estimate you can actually trust, when the data has temporal structure, as is the case for any production series, lot by lot, day by day.</p>
<h3 id="why-random-cross-validation-leaks-temporal-information">Why random cross-validation leaks temporal information</h3>
<p>Standard cross-validation (<code>KFold</code>) shuffles rows and splits them into random folds, assuming observations are independent of one another. In production data that assumption is false by construction: a lot produced on Tuesday is statistically similar to Monday’s lot (same shift, same tool, same accumulated wear), and derived variables — rolling averages, lag features — are built <strong>from</strong> neighboring observations in time. When random shuffling puts a Tuesday observation in the training set and Monday’s in the test set, the model is, in practice, being tested with information that “knows the future” relative to that point — the same information-leakage problem already discussed in <a href="#/aula/cap-111">Chapter 111</a>, except this time introduced by the validation method itself, not by a specific variable.</p>
<p>The symptom is always the same: an overly optimistic validation performance that doesn’t hold up in production.</p>
<h3 id="timeseriessplit-validation-that-respects-chronological-order">TimeSeriesSplit: validation that respects chronological order</h3>
<p>Scikit-learn’s <code>TimeSeriesSplit</code> solves this with an <strong>expanding window</strong>: the first fold trains on the oldest data and tests on the following block; the second fold includes that block in training and tests on the next one; and so on. The training set never contains observations that come after the corresponding test block — in any fold.</p>
<p><div class="math-block" data-math="\text{Fold } k:\quad \text{train} = \{1, \dots, t_k\},\quad \text{test} = \{t_k{+}1, \dots, t_{k+1}\}"></div></p>
<p>Compared to <code>KFold</code>, this has a cost: each fold uses less training data than a random split with the same proportion would, and the earliest folds have very little data. It’s an acceptable price — the alternative is a performance estimate that isn’t valid for the model’s actual use.</p>
<h3 id="hierarchical-split-train-inner-validation-and-untouched-outer-test">Hierarchical split: train, inner validation, and an untouched outer test set</h3>
<p>There’s a second, subtler source of leakage called <em>data snooping</em>: if the same test set is reused repeatedly to compare dozens of hyperparameter combinations, the best combination found will be partially “fit” to that specific test set — even with no single variable leaked, just from the repeated selection process itself. The fix is a three-way chronological split, never two:</p>
<ul>
<li><strong>Train</strong> — where the model’s parameters are fit.</li>
<li><strong>Inner validation</strong> — where hyperparameters and the decision threshold (see <a href="#/aula/cap-169">Chapter 169</a>) are chosen, with as many iterations as needed.</li>
<li><strong>Outer test</strong> — touched <strong>exactly once</strong>, at the end, only to report the expected performance. No modeling decision may depend on the result on this block.</li>
</ul>
<p>In practice, this means applying <code>TimeSeriesSplit</code> <strong>inside</strong> the train+inner-validation block, keeping the outer test block completely outside the selection process — a nested split, not a single chronological split.</p>

import pandas as pd
from sklearn.linear_model import Ridge
from sklearn.model_selection import KFold, TimeSeriesSplit, GridSearchCV
from sklearn.metrics import mean_absolute_error

rng = np.random.default_rng(2026)
n = 900  # ~900 days of production, one row per day

# --- Series with slow trend (tool wear) + noise ---
t = np.arange(n)
tendencia = 0.015 * t
sazonal = 3.0 * np.sin(2 * np.pi * t / 7)     # weekly pattern
ruido = rng.normal(0, 2.0, n)
producao = 120 + tendencia + sazonal + ruido

df = pd.DataFrame({"dia": t, "producao": producao})
df["lag1"] = df["producao"].shift(1)
df["lag7"] = df["producao"].shift(7)
df["media_movel_7"] = df["producao"].shift(1).rolling(7).mean()
df = df.dropna().reset_index(drop=True)

X = df[["dia", "lag1", "lag7", "media_movel_7"]]
y = df["producao"]

# --- Final reserve: outer test, never used until the last line ---
corte_teste = int(0.85 * len(df))
X_dev, X_teste = X.iloc[:corte_teste], X.iloc[corte_teste:]
y_dev, y_teste = y.iloc[:corte_teste], y.iloc[corte_teste:]

modelo = Ridge()
grade = {"alpha": [0.1, 1.0, 5.0, 20.0]}

# --- Comparison: random KFold vs. TimeSeriesSplit, both on the DEV block only ---
for nome, cv in [("Random KFold (WRONG for time series)", KFold(n_splits=5, shuffle=True, random_state=0)),
                  ("TimeSeriesSplit (correct)", TimeSeriesSplit(n_splits=5))]:
    busca = GridSearchCV(modelo, grade, cv=cv, scoring="neg_mean_absolute_error")
    busca.fit(X_dev, y_dev)
    mae_cv = -busca.best_score_
    pred_teste = busca.best_estimator_.predict(X_teste)
    mae_teste_real = mean_absolute_error(y_teste, pred_teste)
    print(f"{nome}")
    print(f"  best alpha           = {busca.best_params_['alpha']}")
    print(f"  MAE estimated in CV  = {mae_cv:.3f}")
    print(f"  real MAE on the outer test set (never seen) = {mae_teste_real:.3f}")
    print(f"  CV optimism (MAE_test - MAE_cv) = {mae_teste_real - mae_cv:+.3f}\n")</code></pre></div></div></div><p><strong>Engineering reading.</strong> Random <code>KFold</code> tends to produce a more optimistic (lower) validation MAE than the real MAE observed on the outer test set, because every training fold contains immediate temporal neighbors of that fold’s test block — exactly the leakage pattern described above. <code>TimeSeriesSplit</code> produces an estimate closer to the real one, at the cost of using less data in each fitting fold.</p>
<h3 id="gridsearchcv-searching-hyperparameters-without-leaking-the-test-set">GridSearchCV: searching hyperparameters without leaking the test set</h3>
<p><code>GridSearchCV</code> automates repeating fit+evaluate for every hyperparameter combination in a grid, using the cross-validation scheme passed in <code>cv</code> — for temporal data, a <code>TimeSeriesSplit</code>, never the random default. The <code>scoring</code> parameter should use the right metric for the problem: for imbalanced classification, <code>average_precision</code> (PR-AUC, see <a href="#/aula/cap-169">Chapter 169</a>) is usually preferable to <code>accuracy</code>. After the search, <code>best_estimator_</code> is the model already refit with the best combination on the whole development block — ready to be evaluated, exactly once, on the outer test set.</p>
<p>With this validation framework in place, the next chapter uses it to fairly compare three model families: regularized linear regression, Random Forest, and Gradient Boosting.</p>

<h3 id="common-mistakes">Common mistakes</h3>
<ol>
<li><strong>Using random <code>KFold</code> or <code>train_test_split</code> on data with temporal structure.</strong> This is the most common mistake and the quietest one — the code runs without error, only the performance estimate is overly optimistic.</li>
<li><strong>Choosing hyperparameters by looking directly at the outer test set.</strong> Always use an inner validation set within the development block; the outer test set is touched exactly once.</li>
<li><strong>Building lag features before splitting train and test.</strong> If <code>rolling()</code>/<code>shift()</code> is computed on the whole dataframe before the split, information from the test period can leak into the training period’s variables in certain implementations — always check the direction of the <code>shift</code>.</li>
<li><strong>Assuming more folds is always better.</strong> With few observations, too many folds leave the earliest training windows too small for the model to stabilize.</li>
<li><strong>Comparing cross-validation MAE/AUC directly with another project’s.</strong> It’s only comparable if the validation scheme (random vs. temporal, number of folds) is the same.</li>
</ol>
