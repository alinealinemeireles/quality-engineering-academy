## Chapter 901: Spaghetti Diagram, Makigami and Turtle Diagram — the Three That Were Missing

### First: which one, and when

They aren't alternatives — they're layers. Hover over each bubble to see what it's for.

```plotly

```

The useful reading of this chart isn't the individual position, it's the **diagonal**: the deeper
the information, the more expensive the map. A well-run project climbs that diagonal only as far
as it needs to. Doing BPMN for a linear three-step process is waste; doing only a flowchart for a
process that crosses five departments is naive.

## 1 · Spaghetti diagram

### The engineering question

*Everyone agrees the cell is "well organized." So why does the operator walk 4 km per shift?*

Because nobody measured it. The spaghetti diagram is Lean's cheapest tool and one of its most
persuasive: you draw the layout of the workstation or cell and **trace with a pencil the actual
path** taken by a person, a part, or a document during one cycle. The name comes from the
result — the trace of a poorly laid-out process looks like a plate of spaghetti.

What makes it powerful isn't the technique, it's the effect in the room: a supervisor who defends
the layout for an hour goes quiet when they see their own path drawn out.

### How to do it, in seven steps

1. **Draw the layout to scale.** A ruler sketch is enough; what it can't be is "roughly."
2. **Choose the subject.** Operator, part, or information — **one at a time**. Mixing all three
   in one map is mistake #1.
3. **Choose the cycle.** A full shift, or a whole number of parts. Never "a bit."
4. **Follow and trace in real time.** Don't reconstruct from memory, and don't ask "where do you
   usually go."
5. **Count.** Number of trips, total distance, time spent moving.
6. **Convert to money and to takt.** Meters ÷ walking speed (≈ 1.2 m/s on a factory floor) = time.
   Compare that time with the takt time.
7. **Redesign the layout and trace again.** The second trace is the proof.

### Calculating distance from the trace

If you record the station coordinates and the sequence visited, the distance comes out as the sum
of Euclidean distances — and from there to time and cost is just arithmetic.

```py-r
--- python
import numpy as np

# station coordinates, in meters
postos = {
    "Warehouse": (3.2, 26.9), "Cutting": (10.2, 24.3), "Press": (20.5, 25.3),
    "Bench": (12.8, 16.0), "Deburring": (25.6, 17.9), "Washing": (6.4, 9.6),
    "Inspection": (23.0, 8.3), "Packaging": (30.1, 27.5), "Shipping": (30.7, 4.5),
}

atual = ["Warehouse","Cutting","Bench","Press","Bench","Deburring","Washing",
         "Bench","Inspection","Washing","Packaging","Bench","Shipping"]
futuro = ["Warehouse","Cutting","Press","Deburring","Washing","Inspection",
          "Packaging","Shipping"]

def percurso(seq):
    p = np.array([postos[s] for s in seq])
    passos = np.linalg.norm(np.diff(p, axis=0), axis=1)
    return passos.sum(), len(passos), passos

VELOCIDADE = 1.2      # m/s, factory-floor walking speed
PECAS_DIA  = 420

for nome, seq in [("Current state", atual), ("Future state", futuro)]:
    d, n, passos = percurso(seq)
    print(f"{nome:15s} {d:6.1f} m   {n:2d} trips   "
          f"largest jump {passos.max():.1f} m   {d/VELOCIDADE:5.1f} s/part")

d0, _, _ = percurso(atual)
d1, _, _ = percurso(futuro)
poupanca_h = (d0 - d1) * PECAS_DIA / VELOCIDADE / 3600
print()
print(f"Reduction: {(1-d1/d0)*100:.0f}%  ->  {poupanca_h:.1f} h/day of walking eliminated")
print(f"At 18 EUR/h fully-loaded station cost: {poupanca_h*18*220:,.0f} EUR/year".replace(",", " "))
--- r
# station coordinates, in meters
postos <- data.frame(
  posto = c("Warehouse","Cutting","Press","Bench","Deburring",
            "Washing","Inspection","Packaging","Shipping"),
  x = c(3.2, 10.2, 20.5, 12.8, 25.6, 6.4, 23.0, 30.1, 30.7),
  y = c(26.9, 24.3, 25.3, 16.0, 17.9, 9.6, 8.3, 27.5, 4.5)
)

atual <- c("Warehouse","Cutting","Bench","Press","Bench","Deburring","Washing",
           "Bench","Inspection","Washing","Packaging","Bench","Shipping")
futuro <- c("Warehouse","Cutting","Press","Deburring","Washing","Inspection",
            "Packaging","Shipping")

percurso <- function(seq) {
  p <- postos[match(seq, postos$posto), c("x", "y")]
  passos <- sqrt(diff(p$x)^2 + diff(p$y)^2)
  list(total = sum(passos), n = length(passos), passos = passos)
}

VELOCIDADE <- 1.2
PECAS_DIA  <- 420

for (nm in c("Current state", "Future state")) {
  seq <- if (nm == "Current state") atual else futuro
  r <- percurso(seq)
  cat(sprintf("%-15s %6.1f m   %2d trips   largest jump %.1f m   %5.1f s/part\n",
              nm, r$total, r$n, max(r$passos), r$total / VELOCIDADE))
}

d0 <- percurso(atual)$total
d1 <- percurso(futuro)$total
poupanca_h <- (d0 - d1) * PECAS_DIA / VELOCIDADE / 3600
cat(sprintf("\nReduction: %.0f%%  ->  %.1f h/day of walking eliminated\n",
            (1 - d1/d0) * 100, poupanca_h))
cat(sprintf("At 18 EUR/h fully-loaded station cost: %s EUR/year\n",
            format(round(poupanca_h * 18 * 220), big.mark = " ")))
--- excel
' Distance between two stations (coordinates in A2:B10, sequence in D2:D14)

' Distance of one step:
=SQRT((INDEX($A$2:$A$10,MATCH(D3,$C$2:$C$10,0))-INDEX($A$2:$A$10,MATCH(D2,$C$2:$C$10,0)))^2
     +(INDEX($B$2:$B$10,MATCH(D3,$C$2:$C$10,0))-INDEX($B$2:$B$10,MATCH(D2,$C$2:$C$10,0)))^2)

' Total distance:
=SUM(E2:E13)

' Time per part (s):
=E15/1.2

' Hours per day eliminated:
=(E15_current-E15_future)*420/1.2/3600
```

### Common mistakes

1. **Tracing from memory.** The remembered path is always shorter and cleaner than the real one.
2. **Mixing subjects.** One map for the operator, another for the part. If they cross, that's
   already a finding — but in separate maps.
3. **Measuring a "normal" day.** It doesn't exist. Trace at least two cycles and show both.
4. **Stopping at the drawing.** Without meters and seconds, the spaghetti trace is decorative art.
5. **Optimizing the layout without looking at material flow.** Shortening the operator's path by
   increasing part transport just swaps one waste for a bigger one.

## 2 · Makigami

### The engineering question

*VSM works well on the shop floor. How do you map a process where no part moves at all — just
information, approvals, and waiting?*

**Makigami** (巻紙, literally "paper roll") is the Japanese answer to that: an administrative
process map in horizontal layers, drawn on a roll of wallpaper in a room with every area involved
present. It's the VSM of transactional processes.

The structure is always the same — columns are steps, rows are layers:

| Layer | What gets recorded | Why it matters |
|---|---|---|
| **Activity** | What gets done, verb in the infinitive | The map's backbone |
| **Owner** | Who, by role name | Reveals handoffs, like the swimlane |
| **Document / system** | Which form, which screen, which email | Where information gets re-created |
| **Processing time** | Minutes of actual work | The numerator of the VA ratio |
| **Passage time** | Start to finish, including waiting | The denominator — almost always shocking |
| **Problems** | Rework, questions, returns | Feeds the cause Pareto |
| **Ideas** | What the team proposes right there | Keeps the session from dying at diagnosis |

### What Makigami exposes that nothing else does

A customer order that "takes two days" in the team's perception. Hover over each bar:


be invisible next to the waiting ones — which is exactly the problem.*

Notice the practical consequence: **speeding up the activities fixes nothing**. If the team
doubled productivity in all six steps, the process would go from 40.4 h to 39.7 h — a 1.7%
improvement. All the gain is in the waits, and the waits live at the boundaries between areas, not
inside them.

This is the same argument as the pool/lane golden rule from the previous chapter, now with
numbers.

### How to run a Makigami session

- **Physical room, physical paper, sticky notes.** The tool works because everyone sees it at the
  same time. Done in software by one person, it's just an ugly flowchart.
- **Every area present.** Half the value is in the sentences "oh, but I didn't know you did
  that."
- **Passage time measured, not estimated.** Pull it from the system: date/time in and out of each
  step. Estimates underrate the wait by a factor of 3 to 10.
- **Two sticky-note colors:** problems and ideas. Keeping them separate stops the session from
  degenerating into complaining or jumping straight to a solution.

### Makigami and VSM: when to use which

| | VSM | Makigami |
|---|---|---|
| Object | Physical part | Information / document |
| Information flow | Separate layer, on top | Is the object itself |
| Inventory | Parts between stations | Requests in a queue, inboxes |
| Key metric | Lead time, VA ratio | Passage time, VA ratio |
| Layers | 2 (material + information) | 5 to 7 |
| Typical mistake | Ignoring the information flow | Estimating the wait instead of measuring it |

## 3 · Turtle diagram

### The engineering question

*The auditor is about to arrive and ask "show me this process." What goes on the table?*

The **turtle diagram** exists for exactly that. It's the representation of a process from a
management-system viewpoint: not the sequence of steps, but **the six questions the standard
wants answered**. The name comes from the shape: a body (the process), a head (inputs), a tail
(outputs), and four legs.

It's the go-to tool for preparing **IATF 16949** and **ISO 9001** audits, and it's also the basis
for process-based auditing: the auditor enters through one leg and checks whether the other five
are consistent with it.

### How the auditor uses it (and how to prepare for that)

A process audit enters through one leg and checks **consistency with the other five**. The
classic paths:

| The auditor enters through… | And goes on to check… | The failure they're looking for |
|---|---|---|
| **Indicators** | Whether the target exists, is measured, and what happens when it's missed | An indicator that measures activity instead of effectiveness |
| **With what** | Calibration of the instrument that generates that indicator | An overdue instrument feeding a conformity decision |
| **With whom** | Whether whoever performs the work is qualified for that method | An operator running a test they aren't qualified for |
| **How** | Whether the written procedure describes what's actually done | The procedure-vs-practice gap — the single most common nonconformity |
| **Inputs** | Where it comes from, and whether that process declares it as an output | An orphan input: nobody formally produces it |
| **Outputs** | Who it goes to, and whether that someone recognizes it as an input | An output nobody receives: wasted work |

**The preparation that works** isn't writing pretty turtles the night before. It's checking, for
each process, whether the six boxes close on each other — and above all whether the **inputs and
outputs mesh with those of neighboring processes**. An organization whose turtles all mesh
together actually has a system; one whose turtles were written in isolation has a collection of
sheets of paper.

### Common mistakes

1. **Confusing the turtle with a flowchart.** It doesn't describe a sequence. If you put numbered
   steps in the body, you've missed the point.
2. **Activity indicators instead of effectiveness indicators.** "Number of inspections performed"
   isn't an indicator of the inspection process; "escape rate to the customer" is.
3. **One turtle per department.** It's per **process**. A process can cross three departments —
   and that's exactly where the turtle is useful.
4. **Writing it for the audit.** A turtle written the night before shows, because its inputs and
   outputs don't mesh with those of the neighboring processes.
5. **Leaving the "How" leg empty or generic.** It's the one the auditor checks against the actual
   workstation.
