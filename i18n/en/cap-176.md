## Chapter 176: Connecting Python to Databases: SQLAlchemy, pyodbc, and Bulk Loading

<h3 id="a-pergunta-de-engenharia">The engineering question</h3>
<p><em>Chapter 107 taught you how to write the right query. But when the pipeline has to run on its own — every night, with nobody copying and pasting SQL into a client — who opens the connection, authenticates, creates the database if it doesn't exist yet, and loads 50,000 rows without taking twenty minutes?</em></p>
<p>That's the boundary between "I know SQL" and "I know how to build a data pipeline." This chapter covers the layer that connects Python to SQL Server: connection engine, authentication, bulk loading, and running administrative scripts — exactly what a data-access library (the <code>db_lib</code> of a real manufacturing analytics project) needs to solve before any analysis can begin.</p>
<h3 id="from-interactive-query-to-a-pipeline-that-runs-on-its-own">From interactive query to a pipeline that runs on its own</h3>
<p>An interactive SQL client (Azure Data Studio, SSMS, a notebook's own <code>%%sql</code>) asks you for credentials once, keeps the connection open while you work, and lets you fix a syntax error on the spot. A production pipeline has nobody watching the screen: it needs to open and close the connection by itself, know what to do if the target database doesn't exist yet, and run <strong>idempotently</strong> — runnable from scratch, as many times as needed, without depending on state left over from the previous run.</p>
<p>In Python, the layer that solves "how do I connect" is typically <strong>SQLAlchemy</strong> (the connection and execution abstraction engine), backed by an <strong>ODBC driver</strong> — for SQL Server, that's <code>pyodbc</code>. SQLAlchemy doesn't replace the SQL you already know how to write: it manages the connection, the connection pool, and the translation between the connection string and the driver's protocol.</p>
<h3 id="sqlalchemy-engine-odbc-driver-and-windows-authentication">SQLAlchemy: engine, ODBC driver, and Windows authentication</h3>
<p>SQLAlchemy's central object is the <strong>engine</strong> — created once, reused across the whole application. For SQL Server with integrated Windows authentication (common in corporate environments, with no password in the code), the connection string uses the ODBC driver and the <code>Trusted_Connection</code> parameter:</p>

<p>Notice the <code>fast_executemany=True</code> parameter passed directly to <code>create_engine</code> — it's the simplest way to enable pyodbc's bulk-loading optimization; the more explicit alternative is registering a listener on the <code>before_cursor_execute</code> event that sets <code>cursor.fast_executemany = True</code> before each batch execution. Both approaches do the same thing; the first is sufficient in most cases with recent versions of SQLAlchemy.</p>
<h3 id="why-pandas-to-sql-doesn-t-scale-to-tens-of-thousands-of-rows">Why pandas.to_sql() doesn't scale to tens of thousands of rows</h3>
<p><code>DataFrame.to_sql()</code> is convenient for exploring data — but, in default mode, it inserts row by row: each <code>INSERT</code> is a separate round trip to the server. For 40 rows that's unnoticeable; for 40,000, network latency multiplied by 40,000 round trips completely dominates execution time, to the point where a load that should take seconds ends up taking tens of minutes.</p>
<p>pyodbc's <code>fast_executemany</code> technique solves this by <strong>grouping many rows into a single packet</strong> sent to the server, instead of one round trip per row. The performance gain reported by practitioners in public benchmarks is typically one or two orders of magnitude compared to pyodbc's naive <code>executemany</code> without that option.</p>

         for i in range(n)]

def carga_linha_a_linha(dados):
    con = sqlite3.connect(":memory:")
    con.execute("CREATE TABLE medicao (id INTEGER, maquina TEXT, valor REAL)")
    t0 = time.perf_counter()
    for linha in dados:
        con.execute("INSERT INTO medicao VALUES (?,?,?)", linha)
    con.commit()
    dt = time.perf_counter() - t0
    con.close()
    return dt

def carga_em_lote(dados, tamanho_lote=2000):
    """Local analog to fast_executemany: groups several rows per
    'round trip' instead of inserting one row at a time."""
    con = sqlite3.connect(":memory:")
    con.execute("CREATE TABLE medicao (id INTEGER, maquina TEXT, valor REAL)")
    t0 = time.perf_counter()
    for i in range(0, len(dados), tamanho_lote):
        lote = dados[i:i + tamanho_lote]
        con.executemany("INSERT INTO medicao VALUES (?,?,?)", lote)
    con.commit()
    dt = time.perf_counter() - t0
    con.close()
    return dt

dt_linha = carga_linha_a_linha(dados)
dt_lote = carga_em_lote(dados)

print(f"Row-by-row insert : {dt_linha:.3f}s")
print(f"Batched insert     : {dt_lote:.3f}s")
print(f"Improvement factor : {dt_linha / dt_lote:.1f}x")
print()
print("Note: in-memory SQLite is already fast, so the difference here comes")
print("only from the number of Python/driver calls, without network. Against a")
print("real SQL Server instance on a corporate network, the same batching")
print("logic (via cursor.fast_executemany=True in pyodbc) typically")
print("multiplies the gain, because it eliminates a network round trip per")

<p><strong>Engineering reading.</strong> The <code>load_dataframe</code> pattern of a real loading library typically combines three decisions: (1) using <code>fast_executemany</code> for the performance gain above; (2) sizing the cursor's parameter buffer via <code>cursor.setinputsizes()</code> when column types vary widely, to prevent pyodbc from inferring the wrong types from the first few rows; and (3) doing a <strong>truncate-and-reload</strong> (wiping and reloading the entire target table) instead of attempting a row-by-row <em>upsert</em> — simpler to make idempotent, and faster when the target table comfortably fits a full reload.</p>
<h3 id="creating-the-database-conditionally-why-outside-a-transaction">Creating the database conditionally: why outside a transaction</h3>
<p>An idempotent pipeline that runs from scratch needs to answer "does the database already exist?" before trying to use it. SQL Server's <code>CREATE DATABASE</code> command has a quirk that surprises people coming from other engines: it <strong>cannot run inside an explicit transaction</strong> — it must run in <em>autocommit</em> mode, outside a <code>BEGIN TRAN</code> block. The correct practice is:</p>

    """Creates the database if it doesn't exist. CREATE DATABASE has to run
    in autocommit mode -- outside an explicit SQL Server transaction."""
    # engine.execution_options(isolation_level="AUTOCOMMIT") turns off
    # SQLAlchemy's automatic transaction wrapping for this connection
    with engine.connect().execution_options(isolation_level="AUTOCOMMIT") as conn:
        existe = conn.exec_driver_sql(
            "SELECT database_id FROM sys.databases WHERE name = ?", (database,)
        ).fetchone()
        if existe is None:
            conn.exec_driver_sql(f"CREATE DATABASE [{database}]")
            print(f"Database '{database}' created.")
        else:
            print(f"Database '{database}' already exists -- nothing to do.")

<h3 id="multi-batch-scripts-why-split-on-go">Multi-batch scripts: why split on GO</h3>
<p>Schema definition scripts (<code>CREATE TABLE</code>, <code>CREATE VIEW</code>, schema changes) often come in a single <code>.sql</code> file with multiple commands separated by the <code>GO</code> keyword. <code>GO</code> is <strong>not a SQL statement</strong> — it's a T-SQL client convention (SSMS, <code>sqlcmd</code>) that says "send everything accumulated so far as a separate <em>batch</em>." The pyodbc driver doesn't understand <code>GO</code> natively: a script with several blocks separated by <code>GO</code> has to be <strong>split in Python before being sent</strong>, one batch at a time.</p>
<div class="codetabs"><div class="ct-bar" role="tablist"><button type="button" class="ct-tab on" role="tab" aria-selected="true" id="cte1eac9f6-t0">Python</button></div><div class="ct-pane" role="tabpanel" aria-labelledby="cte1eac9f6-t0"><div class="codeblock" data-lang="python"><div class="codebar"><span class="lang">Python</span><button class="btn-copy" type="button">Copiar</button></div><pre><code class="language-python">import re

def _split_on_go(script_sql):
    """Splits a T-SQL script into batches separated by the 'GO' line,
    ignoring case and surrounding whitespace."""
    lotes = re.split(r"(?im)^\s*GO\s*$", script_sql)
    return [lote.strip() for lote in lotes if lote.strip()]

script = """
CREATE TABLE dim_maquina (id_maquina INT PRIMARY KEY, nome TEXT);
GO
CREATE TABLE fato_producao (id INT PRIMARY KEY, id_maquina INT, qtd INT);
GO
CREATE VIEW vw_producao_por_maquina AS
    SELECT id_maquina, SUM(qtd) AS total FROM fato_producao GROUP BY id_maquina;
GO
"""

lotes = _split_on_go(script)
print(f"Script split into {len(lotes)} batches:")
for i, lote in enumerate(lotes, start=1):
    primeira_linha = lote.splitlines()[0]
    print(f"  Batch {i}: {primeira_linha}")

def run_sql_script(engine, script_sql):
    """Runs each batch separately -- the pattern used to apply full
    schema scripts (tables + views) in a single pipeline step."""
    with engine.begin() as conn:
        for lote in _split_on_go(script_sql):
            conn.exec_driver_sql(lote)</code></pre></div></div></div>
<p>This pattern closes the loop: a schema script written and tested manually in a SQL client (where <code>GO</code> works natively) can now be applied by a Python pipeline without rewriting anything — you just need to split the text before sending it through the driver.</p>

<h3 id="common-mistakes">Common mistakes</h3><ol>
<li><strong>Storing the password as plain text in the code.</strong> With integrated Windows authentication (<code>Trusted_Connection</code>/<code>trusted_connection=yes</code>), there's no password to manage — the identity of the process running the pipeline is the credential.</li>
<li><strong>Using <code>pandas.to_sql()</code> without <code>method="multi"</code> or without an engine with <code>fast_executemany</code> for large volumes.</strong> Works for prototypes; in production, with tens of thousands of rows, it becomes the whole pipeline's bottleneck.</li>
<li><strong>Trying <code>CREATE DATABASE</code> inside an explicit SQLAlchemy transaction.</strong> SQL Server rejects it — the command needs to run in autocommit mode.</li>
<li><strong>Sending an entire script with several <code>GO</code>s as a single string to the driver.</strong> <code>GO</code> is a client convention, not a SQL statement — the driver doesn't know what to do with it and the script either fails or gets interpreted as a single invalid batch.</li>
<li><strong>Not designing the pipeline to be idempotent.</strong> A pipeline that only works "the first time" can't be safely rerun after a mid-run failure — truncate-and-reload is simpler to make safe than partial upserts.</li>
