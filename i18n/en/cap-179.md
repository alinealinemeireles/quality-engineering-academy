## Chapter 179: Data Pipeline Engineering in Pandas: groupby/transform, Interval Matching, and Stateful Sequencing

<h3 id="a-pergunta-de-engenharia">The engineering question</h3>
<p><em>Three real situations from a manufacturing pipeline: (1) the material batch number is blank on some rows, but should inherit the value from the previous event on the same machine; (2) a machine stoppage needs to be linked to the production order that was running at that exact instant — and, if two orders overlap, to the most recent one; (3) a material batch's sequential number can only be computed by looking, one row at a time, at what's already been seen. None of these three operations is a simple aggregation — and none of them is solved with a one-line vectorized function.</em></p>
<p>This chapter covers the pandas that sits between "I know how to do <code>groupby().sum()</code>" and "I know how to build a cleaning pipeline that survives the real, messy cases of a shop floor."</p>
<h3 id="the-bridge-you-already-know-groupby-transform-is-partition-by-over">The bridge you already know: groupby().transform() is PARTITION BY ... OVER</h3>
<p>In <a href="#/aula/cap-107">Chapter 107</a> you saw <code>SUM(x) OVER (PARTITION BY ...)</code> — an aggregation computed within each partition, but returned at the same granularity as the original rows (unlike <code>GROUP BY</code>, which collapses rows). In pandas, the exact equivalent is <code>groupby(coluna).transform(funcao)</code>: it groups, applies the function to each group, and returns a result with the <strong>same index and the same shape</strong> as the original DataFrame — ready to be assigned back as a new column.</p>
<p>This equivalence is the key to not treating <code>transform()</code> as magic: it's the same partitioned-window operation you already saw in SQL, just expressed in pandas syntax.</p>

<p>Not all logic is vectorizable. A <strong>stateful sequencing</strong> — where the current row's value depends on a decision made in previous rows, not just on the row's own values — is the classic case where an explicit, row-by-row loop is simpler and more correct than forcing an artificial vectorized solution. A real-world example: assigning a new material batch sequence number every time the batch reference changes within the same machine, but keeping the previous number while the reference stays the same.</p>
<h3 id="worked-example-stateful-sequencing-loop-vs-vectorized-alternative">Worked example: stateful sequencing — loop vs. vectorized alternative</h3><div class="codetabs"><div class="ct-bar" role="tablist"><button type="button" class="ct-tab on" role="tab" aria-selected="true" id="ct75b83107-t0">Python</button></div><div class="ct-pane" role="tabpanel" aria-labelledby="ct75b83107-t0"><div class="codeblock" data-lang="python"><div class="codebar"><span class="lang">Python</span><button class="btn-copy" type="button">Copy</button></div><pre><code class="language-python">import pandas as pd

df = pd.DataFrame({
    "maquina": ["M1"]*6,
    "hora":    [1, 2, 3, 4, 5, 6],
    "lote_material": ["LOT-A", "LOT-A", "LOT-B", "LOT-B", "LOT-B", "LOT-C"],
})

def sequenciar_lote(grupo):
    """Increments the sequence number only when the batch changes -- it
    depends on the PREVIOUS row's value, so it's not directly vectorizable."""
    seq = []
    lote_atual = None
    contador = 0
    for lote in grupo["lote_material"]:
        if lote != lote_atual:
            contador += 1
            lote_atual = lote
        seq.append(contador)
    grupo = grupo.copy()
    grupo["seq_lote"] = seq
    return grupo

resultado = df.groupby("maquina", group_keys=False).apply(sequenciar_lote)
print(resultado.to_string(index=False))
print()
print("Equivalent vectorized alternative, for anyone who'd rather avoid the")
print("explicit Python loop -- it works because 'value change' DOES have a")
print("vectorizable form via comparison with shift():")
df["seq_lote_vetorizado"] = (
    df["lote_material"].ne(df["lote_material"].shift()).cumsum()
)
print(df.to_string(index=False))

<p>A harder problem still: linking a point-in-time event (a machine stoppage, with a single instant) to the production order that was active <strong>on that machine, at that instant</strong> — knowing that production orders have a start and end, can overlap due to a data-entry error, and require a tie-breaking rule when that happens. This is an <strong>interval match</strong>, not a direct <code>merge</code>: there's no shared key between the two tables, there's a condition — "the stoppage's instant falls inside the order's interval, on the same machine."</p>
<h3 id="worked-example-matching-a-stoppage-to-a-production-order-with-a-tie-break">Worked example: matching a stoppage to a production order, with a tie-break</h3><div class="codetabs"><div class="ct-bar" role="tablist"><button type="button" class="ct-tab on" role="tab" aria-selected="true" id="ctd5d92877-t0">Python</button></div><div class="ct-pane" role="tabpanel" aria-labelledby="ctd5d92877-t0"><div class="codeblock" data-lang="python"><div class="codebar"><span class="lang">Python</span><button class="btn-copy" type="button">Copy</button></div><pre><code class="language-python">import pandas as pd

paragens = pd.DataFrame({
    "maquina": ["M1", "M1"],
    "instante_paragem": pd.to_datetime(["2026-08-01 10:15", "2026-08-01 14:40"]),
})

ordens = pd.DataFrame({
    "maquina": ["M1", "M1", "M1"],
    "ordem_id": ["OP-100", "OP-101", "OP-102"],
    "inicio": pd.to_datetime(["2026-08-01 08:00", "2026-08-01 10:00", "2026-08-01 14:00"]),
    "fim":    pd.to_datetime(["2026-08-01 10:30", "2026-08-01 14:30", "2026-08-01 18:00"]),
})
# Note: OP-100 and OP-101 overlap between 10:00 and 10:30 -- a typical
# duplicate record from a real MES. The 10:15 stoppage falls in both.

def encontrar_ordem(paragem, ordens_maquina):
    candidatas = ordens_maquina[
        (ordens_maquina["inicio"] &lt;= paragem) &amp; (paragem &lt;= ordens_maquina["fim"])
    ]
    if candidatas.empty:
        return None
    # Tie-break rule: among overlapping candidates, keep the one that
    # started latest (the "most recent" one in effect at that instant).
    return candidatas.sort_values("inicio", ascending=False).iloc[0]["ordem_id"]

resultados = []
for _, p in paragens.iterrows():
    ordens_maq = ordens[ordens["maquina"] == p["maquina"]]
    ordem = encontrar_ordem(p["instante_paragem"], ordens_maq)
    resultados.append(ordem)

paragens["ordem_associada"] = resultados
print(paragens.to_string(index=False))
print()
print("The 10:15 stoppage fell within OP-100 (08:00-10:30) AND OP-101")
print("(10:00-14:30) -- two valid orders at the same time. The tie-break")
print("rule picked OP-101 (the one that started later). Without that")
print("explicit rule, the result would depend on the arbitrary row order")
print("in the table -- a silent bug, hard to catch in real data where")
print("overlaps are rare but not nonexistent.")</code></pre></div></div></div>
<p><strong>Engineering reading.</strong> This pattern doesn't have a ready-made pandas function — it's explicit business logic, and the tie-break rule ("keep the most recent one") is a decision that needs to be documented, not just coded. A different rule ("keep the shortest one," or "raise a data alert instead of choosing") would produce an equally valid result for a different business context.</p>
<h3 id="data-quality-scorecard-as-a-formal-practice">Data Quality Scorecard as a formal practice</h3>
<p>Each of the transformations above — filling, sequencing, matching — can fail silently: a partition with no non-null value for <code>ffill</code> to inherit, a stoppage with no candidate order, a batch whose sequence never resets. A <strong>Data Quality Scorecard</strong> is the practice of measuring, before and after each pipeline step, indicators like the percentage of missing values, the percentage of unmatched events, and the number of dropped rows — and recording that comparison as part of the pipeline itself, not as an ad-hoc manual check. At minimum, a simple scorecard sums, per column, the null count before and after each transformation and reports the difference — enough to catch whether a change to the cleaning code introduced a silent regression.</p>

<h3 id="common-mistakes">Common mistakes</h3><ol>
<li><strong>Using <code>apply()</code> when <code>transform()</code> would do.</strong> When the result has the same shape as the input, <code>transform()</code> is more direct and avoids unnecessary index reconstruction.</li>
<li><strong>Forcing vectorization onto complex stateful logic.</strong> A well-commented explicit loop is easier to verify than a chain of <code>shift()</code>/<code>cumsum()</code> calls that gets hard to read once the transition rule has more than one condition.</li>
<li><strong>Doing interval matching with a simple key-based <code>merge</code>.</strong> There's no shared key in an interval match — you need an overlap condition, and that condition is rarely 1:1 in real data.</li>
<li><strong>Not defining the tie-break rule before writing the code.</strong> When two candidates are equally valid, letting the code "pick whichever comes first" produces a result that depends on the data's internal row order — not reliably reproducible.</li>
<li><strong>Measuring data quality only once, at the end of the pipeline.</strong> Without a per-step scorecard, a regression introduced midway through the pipeline is only discovered once the final result is already wrong — and by then it's harder to isolate which step the problem started in.</li>
