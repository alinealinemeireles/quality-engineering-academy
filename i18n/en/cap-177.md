## Chapter 177: Dimensional Modeling: Fact, Dimension, and Star Schema

<h3 id="a-pergunta-de-engenharia">The engineering question</h3>
<p><em>An analyst asks: "what was the reject rate by machine, by shift, for the last week, just for supplier X?" The right answer exists somewhere in your tables — but if the schema were designed only for the transactional system that generated the data, that question would require eight JOINs and nobody would be able to answer it in real time.</em></p>
<p>Dimensional modeling solves exactly this problem: organizing data so that analytical questions — "how much, by whom, when, where" — are answered with one or two simple joins, not an archaeology of the transactional schema. A real manufacturing analytics project that follows this pattern ends up with 22 fact tables and 15 dimensions — not by accident, but because that's how Ralph Kimball's method structures any sufficiently rich business domain.</p>
<h3 id="the-problem-dimensional-modeling-solves">The problem dimensional modeling solves</h3>
<p>A transactional system (the ERP, the MES, the database that records each event as it happens) is designed to <strong>write</strong> fast and without duplication — it's normalized, often across dozens of tables linked by foreign keys. That's great for operational integrity and terrible for analysis: answering "what was the total number of parts rejected by supplier last quarter" requires traversing that entire web of tables.</p>
<p>Dimensional modeling, formalized by Ralph Kimball and Margy Ross in <em>The Data Warehouse Toolkit</em> (Wiley, original edition 1996), proposes reorganizing the same data around two table categories: <strong>fact</strong> and <strong>dimension</strong>. The result — when designed correctly — is a <strong>star schema</strong>: a central fact table linked to several dimension tables around it, like the points of a star.</p>
<h3 id="fact-tables-what-happened-quantified">Fact tables: what happened, quantified</h3>
<p>A <strong>fact table</strong> records a <em>measurable business process event</em> — a part produced, a machine stoppage, a nonconformance. Each row is one occurrence of that event, and the columns fall into two families:</p>
<ul>
<li><strong>Foreign keys</strong> to each relevant dimension (which machine, which shift, which day, which product) — the event's "context."</li>
<li><strong>Additive numeric metrics</strong> — quantity produced, downtime in minutes, cost of the nonconformance — numbers that make sense to sum across thousands of rows.</li>
</ul>
<p>A production fact table, for instance, has one row per part produced (or per batch, depending on the chosen grain — the most important decision when designing any fact table), with keys for machine, shift, date, and product, and metrics like quantity and cycle time.</p>
<h3 id="dimension-tables-the-context-that-gives-the-number-meaning">Dimension tables: the context that gives the number meaning</h3>
<p>A <strong>dimension table</strong> describes the "who, what, where, when" around the event — it's typically wide in columns (many descriptive attributes) and short in rows (a few dozen or a few hundred machines, products, suppliers) compared to the fact table, which grows one row per event. The <code>dim_maquina</code> dimension doesn't just store the machine's identifier: it stores the name, the production cell, the manufacturer, the installation date — everything an analyst might want to group or filter by, without going back to the source system.</p>
<p>It's this separation — few, wide dimensions and many, narrow, numerous facts — that turns the question "reject rate by machine, by shift, by supplier" into a direct join between one fact and three dimensions, instead of a traversal of the entire transactional schema.</p>
<h3 id="surrogate-keys-why-not-use-the-source-system-s-key">Surrogate keys: why not use the source system's key</h3>
<p>A core Kimball practice is that every dimension has a <strong>surrogate key</strong> — a sequential integer identifier generated by the warehouse itself, distinct from the business identifier or the source system's code (the machine's serial number, the supplier's code in the ERP). This decouples the analytical model from changes in the operational system: if the ERP is replaced tomorrow, or a supplier's code changes, the surrogate key in the dimension doesn't change — you only need to map the new source code to the same, already-existing surrogate key.</p>

import pandas as pd
import numpy as np

rng = np.random.default_rng(2026)
con = sqlite3.connect(":memory:")

# ---------- Two dimensions (wide, few rows) ----------
con.executescript("""
CREATE TABLE dim_maquina (
    sk_maquina INTEGER PRIMARY KEY,   -- surrogate key, generated here
    codigo_origem TEXT,               -- identifier in the transactional system (MES)
    nome TEXT, celula TEXT, fabricante TEXT
);
CREATE TABLE dim_turno (
    sk_turno INTEGER PRIMARY KEY,
    codigo_origem TEXT, nome TEXT, hora_inicio TEXT, hora_fim TEXT
);
""")

maquinas = [(1, "MES-M001", "Injection molder 1", "Cell A", "Engel"),
            (2, "MES-M002", "Injection molder 2", "Cell A", "Engel"),
            (3, "MES-M003", "Injection molder 3", "Cell B", "Arburg")]
con.executemany("INSERT INTO dim_maquina VALUES (?,?,?,?,?)", maquinas)

turnos = [(1, "T1", "Morning", "06:00", "14:00"),
          (2, "T2", "Afternoon", "14:00", "22:00"),
          (3, "T3", "Night", "22:00", "06:00")]
con.executemany("INSERT INTO dim_turno VALUES (?,?,?,?,?)", turnos)

# ---------- Fact: one row per batch produced ----------
con.execute("""
CREATE TABLE fato_producao (
    sk_maquina INTEGER, sk_turno INTEGER, data TEXT,
    qtd_produzida INTEGER, qtd_rejeitada INTEGER, tempo_paragem_min REAL
)
""")

linhas = []
for _ in range(300):
    linhas.append((
        int(rng.integers(1, 4)), int(rng.integers(1, 4)),
        f"2026-08-{rng.integers(1,29):02d}",
        int(rng.integers(400, 600)),
        int(rng.integers(0, 20)),
        float(round(rng.exponential(8), 1)),
    ))
con.executemany("INSERT INTO fato_producao VALUES (?,?,?,?,?,?)", linhas)
con.commit()

# ---------- The original question: reject rate by machine and shift ----------
q = """
SELECT  dm.nome                                     AS maquina,
        dt.nome                                     AS turno,
        SUM(f.qtd_produzida)                        AS produzido,
        SUM(f.qtd_rejeitada)                        AS rejeitado,
        ROUND(100.0 * SUM(f.qtd_rejeitada)
                    / SUM(f.qtd_produzida), 2)       AS pct_rejeitado
FROM        fato_producao f
JOIN        dim_maquina   dm ON dm.sk_maquina = f.sk_maquina
JOIN        dim_turno     dt ON dt.sk_turno   = f.sk_turno
GROUP BY    dm.nome, dt.nome
ORDER BY    pct_rejeitado DESC
"""
resultado = pd.read_sql_query(q, con)
print(resultado.to_string(index=False))
print()
print("Two joins (fact -&gt; dim_maquina, fact -&gt; dim_turno) are enough to")
print("answer the full question. Note that 'MES-M001' (the source system's")
print("code) never appears in the query -- only the surrogate key is used")
print("to link the tables.")
con.close()</code></pre></div></div></div>
<p>This is exactly the pattern a real manufacturing data warehouse replicates dozens of times: one fact table per measurable business process (production, stoppages, nonconformances, shipments), surrounded by shared dimensions — machine, shift, date, product.</p>
<h3 id="conformed-dimensions-the-same-dimension-reused-across-multiple-fact-tables">Conformed dimensions: the same dimension, reused across multiple fact tables</h3>
<p>When <code>dim_maquina</code> and <code>dim_turno</code> are used not only by <code>fato_producao</code>, but also by <code>fato_paragem</code> and <code>fato_nao_conformidade</code>, they're called <strong>conformed dimensions</strong> — the same definition of "machine," with the same surrogate key, shared by every fact table that needs that context. It's this reuse that lets you compare production and stoppages for the same machine unambiguously, and it's one of the reasons a well-designed dimensional model tends to have few dimensions (dozens) and many fact tables (one per business process).</p>

<h3 id="common-mistakes">Common mistakes</h3><ol>
<li><strong>Using the source system's identifier as the dimension's key.</strong> You lose the decoupling the surrogate key provides — any change in the transactional system propagates straight into the analytical model.</li>
<li><strong>Modeling the fact table at the wrong grain.</strong> Deciding the grain (one row per part? per batch? per shift?) is the first design decision — changing it later forces you to rebuild the entire fact table.</li>
<li><strong>Duplicating a dimension's definition instead of conforming it.</strong> Having two slightly different versions of "machine" (one in each fact table) prevents direct comparisons across processes.</li>
<li><strong>Storing non-additive metrics as if they were additive.</strong> A percentage or an average shouldn't be summed across fact rows — sum the components (numerator and denominator) and compute the ratio afterward, in the query.</li>
<li><strong>Confusing dimensional modeling with normalization.</strong> They're opposite goals: normalization eliminates redundancy for efficient writes; dimensional modeling accepts some controlled redundancy (in the dimensions) for simple analytical reads.</li>
