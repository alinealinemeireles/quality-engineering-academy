## Chapter 26: Jidoka and Poka-Yoke: Quality Built Into the Process
### The engineering question

*Would we rather detect the defect, or prevent it from existing?*

Jidoka and poka-yoke are lean's answer to inspection. Both start from the same diagnosis: **100% human inspection isn't reliable** — the detection rate of repetitive visual inspection typically sits between 80 and 90%, and it degrades with fatigue, pace, and familiarity. Any control plan that depends on "the operator checks" is betting on a measurement system with a mediocre Kappa.

### Jidoka: Autonomation

Jidoka is often translated as "automation with a human touch." The technical content is precise: **the machine has the ability to detect an abnormal condition and stop itself**, without waiting for an operator.

The jidoka cycle has four steps:

1. **Detect** the anomaly (the machine, the sensor, or the operator).
2. **Stop** — production, not just the log entry.
3. **Correct** the immediate condition.
4. **Investigate** the root cause and implement the countermeasure.

The step almost every organization skips is 4. Stopping and restarting without investigating is just crisis management, and it produces the same problem on the next shift.

**Andon.** The visual system that lets the operator signal and stop. The cultural rule that makes it real: **pulling the andon can never have a negative consequence for whoever pulls it.** If it does, the line never stops — and the organization loses its main source of information about problems.

**Human-machine separation.** Jidoka's second consequence: if the machine stops itself when something goes wrong, the operator doesn't need to watch it. One operator can run several machines. This is the original mechanism by which jidoka raised productivity at Toyota — not by speeding anything up.

### Poka-Yoke: Error Prevention

Shingo draws a clear distinction:

$$\text{Error (cause)} \;\longrightarrow\; \text{Defect (effect)}$$

Poka-yoke intervenes on the link. **It isn't "idiot-proofing"** — it's the recognition that competent people make slips on repetitive tasks, and that the station's design should absorb that fact.

**Two functions:**

| Function | When it acts | Effect |
|---|---|---|
| **Control** | Before the defect exists | Physically prevents the error. Preferable. |
| **Warning** | After the error, before it moves forward | Alerts. Depends on human response. |

**Three detection methods:**

1. **Contact** — shape, size, color, weight. The connector that only fits one way.
2. **Fixed value** — count. The kit with exactly 8 bolts; one left over means one operation was skipped.
3. **Motion step** — sequence. The next operation is only possible if the previous one was completed.

**The effectiveness hierarchy** (from strongest to weakest):

1. Eliminate the possibility of the error through product design (a symmetric part, or one impossible to assemble backwards)
2. Replace it with a deterministic automatic process
3. Make the correct way easy and the incorrect way hard (control poka-yoke)
4. Automatically detect before it moves forward (warning poka-yoke)
5. Detect through 100% inspection
6. Detect through sampling
7. Training and work instructions

> A control plan whose controls sit mostly at levels 5–7 is a fragile plan. The PFMEA should drive you up the hierarchy, not add one more inspection.

### Worked example: does the poka-yoke pay off?

An economic comparison between 100% inspection and control poka-yoke, including the effect of human detection reliability.

```py-r
--- python
import pandas as pd
import numpy as np

# --- Cenário ---
volume_anual      = 240_000     # peças/ano
taxa_erro         = 0.008       # 0,8% das peças sofrem o erro de montagem
custo_falha_int   = 12.0        # € por defeito detetado internamente
custo_falha_ext   = 850.0       # € por defeito que chega ao cliente (retorno + logística + risco)
det_inspecao      = 0.85        # eficácia real da inspeção visual 100%
det_pokayoke      = 0.999       # poka-yoke de controlo (contacto)
custo_inspecao_a  = 26_000.0    # € /ano de posto de inspeção
custo_pokayoke    = 4_500.0     # € investimento único (gabarito + sensor)
manut_pokayoke_a  = 600.0       # € /ano de manutenção e verificação

defeitos = volume_anual * taxa_erro
print(f"Defeitos gerados por ano: {defeitos:,.0f}\n")

def custo_anual(nome, deteccao, custo_fixo_anual, investimento=0.0, anos=3):
    detetados = defeitos * deteccao
    escapados = defeitos * (1 - deteccao)
    custo_int = detetados * custo_falha_int
    custo_ext = escapados * custo_falha_ext
    total = custo_int + custo_ext + custo_fixo_anual
    return {"Solução": nome,
            "Deteção": f"{deteccao:.1%}",
            "Defeitos ao cliente/ano": round(escapados),
            "Custo falha interna (€)": round(custo_int),
            "Custo falha externa (€)": round(custo_ext),
            "Custo fixo (€/ano)": round(custo_fixo_anual),
            "TOTAL (€/ano)": round(total),
            "TOTAL 3 anos (€)": round(total * anos + investimento)}

linhas = [
    custo_anual("Sem controlo",       0.0,           0.0),
    custo_anual("Inspeção 100% (visual)", det_inspecao, custo_inspecao_a),
    custo_anual("Poka-yoke de controlo",  det_pokayoke, manut_pokayoke_a, custo_pokayoke),
]
df = pd.DataFrame(linhas)
print(df.to_string(index=False))

melhor = df.loc[df["TOTAL (€/ano)"].idxmin()]
insp = df[df["Solução"].str.startswith("Inspeção")].iloc[0]
poka = df[df["Solução"].str.startswith("Poka")].iloc[0]

print(f"\nPoupança anual do poka-yoke face à inspeção: "
      f"€{insp['TOTAL (€/ano)'] - poka['TOTAL (€/ano)']:,.0f}")
payback_meses = custo_pokayoke / ((insp["TOTAL (€/ano)"] - poka["TOTAL (€/ano)"]) / 12)
print(f"Payback do investimento: {payback_meses:.1f} meses")
print(f"Redução de defeitos que chegam ao cliente: "
      f"{insp['Defeitos ao cliente/ano']:.0f} -> {poka['Defeitos ao cliente/ano']:.0f} por ano")

# --- Sensibilidade à eficácia real da inspeção humana ---
print("\nE se a inspeção visual for melhor ou pior do que pensamos?")
for d in [0.70, 0.80, 0.90, 0.95, 0.99]:
    r = custo_anual("", d, custo_inspecao_a)
    print(f"  deteção {d:.0%} -> custo total €{r['TOTAL (€/ano)']:>9,.0f}"
          f" | escapes {r['Defeitos ao cliente/ano']:>5.0f}"
          f" | poka-yoke ainda vence: {'sim' if r['TOTAL (€/ano)'] > poka['TOTAL (€/ano)'] else 'NÃO'}")
```

**Engineering reading.** Notice what dominates the calculation: **it isn't the cost of the inspection station, it's the cost of the parts that escape.** With 85% detection, 15% of defects reach the customer, and the external cost crushes everything else.

And note the sensitivity analysis: even assuming an optimistic 99% human inspection, the poka-yoke still wins. That's because inspection carries a permanent fixed cost, while the poka-yoke is a one-time investment.

**Important methodological note:** this model's `det_inspecao` parameter shouldn't be assumed. It's measured — with an **Attribute Agreement Analysis** (Kappa), described in PART VI. It's common for an established visual inspection's real effectiveness to be substantially lower than the organization believes.

### Common mistakes

1. **Calling a work instruction a poka-yoke.** "The operator should check" is training (hierarchy level 7), not poka-yoke.
2. **Poka-yoke with no periodic verification.** A broken device no one tests gives false security. The control plan should include the **poka-yoke's functional check** — typically at the start of each shift, with a defective standard part.
3. **Andon with no defined response.** If no one's assigned to respond within X seconds, the andon gets ignored within two weeks.
4. **Stopping the line and not investigating.** Absorbs the disruption and generates no learning.
5. **A poka-yoke that can be bypassed.** If the device can be disabled under production pressure, it will be disabled under production pressure.
