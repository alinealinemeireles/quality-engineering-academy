## Chapter 149: AI, Data, and Model Risk — ISO/IEC 42001 and ISO/IEC 23894
### The engineering question

> *"We put a vision model in charge of approving parts. What documentation, controls, and monitoring
> does that now require — and who's accountable when the model gets it wrong?"*

Once an AI system makes or supports quality decisions, it stops being an analysis tool and becomes
an **element of the control system**. It's now subject to the same demands as any control:
documented validation, change control, monitoring, a reaction plan, and named accountability.

**The two reference standards:**

- **ISO/IEC 42001:2023** — requirements for an **AI management system** (AIMS). It's certifiable and
  follows the high-level structure, integrating with ISO 9001.
- **ISO/IEC 23894:2023** — **guidance** for AI risk management. It applies ISO 31000's logic to the
  specific context of AI.

Chapter 138 covered the technique (validation, calibration, drift). This chapter covers
**governance**: what the organization has to have set up around the model.

---

## 149.1 The AI risk taxonomy applied to quality

| Category | Concrete quality risk | Typical control |
|---|---|---|
| **Data** | Unrepresentative training data; wrong labels; leakage | Data quality profile; labeling audit |
| **Model** | Overfitting; poor calibration; fragility to new conditions | Temporal and group validation; calibration |
| **Drift** | New supplier, new lighting, new variant | PSI and performance monitoring |
| **Use** | Use outside the validated domain | Documented scope-of-use definition |
| **Security** | Input manipulation; unauthorized access | Access controls; input validation |
| **Privacy** | Personal data in images (operators) | Minimization; anonymization; legal basis |
| **Bias** | Different performance by line, shift, or variant | Stratified performance evaluation |
| **Explainability** | Impossible to justify a rejection to the customer | Explanation methods; evidence log |
| **Oversight** | No one can override the model | Defined and logged human authority |
| **Accountability** | No one answers for the error | Named model owner |

---

## 149.2 The eight minimum controls

An organization using AI in quality decisions must have, at minimum:

1. **Model inventory** — which models exist, version, scope of use, owner, date of last validation,
   criticality. Without an inventory, there's no governance — just models.
2. **Documented scope of use** — for which product, which conditions, which limits. A model
   validated on painted parts is not validated on chrome parts, and the boundary has to be written
   down.
3. **Documented validation** — data, method, metrics, known limitations, acceptance criterion.
4. **Change control** — what requires revalidation (the list from Chapter 138), who approves, and
   the record of the decision.
5. **Continuous monitoring** — PSI, calibration, performance on a labeled sample, with thresholds
   and a reaction plan (it's a control plan, and should have the shape of one).
6. **Human oversight** — who can override the model, with what authority, and how it's logged. An
   overridden decision is valuable information about the model.
7. **Traceability** — reconstruct why part X was rejected on day Y by version Z. Requires logging
   the input, output, model version, and threshold in effect.
8. **Fallback plan** — what happens if the model is pulled. If the answer is "we stop the line,"
   that's a continuity risk (Chapter 148) that has to be in the register.

---

## 149.3 FMEA of an AI system

FMEA applies to a model the same way it applies to any other process element — with its own failure
modes:

| Failure mode | Effect | Typical current detection | Improvement |
|---|---|---|---|
| Approves a nonconforming part (FN) | NC reaches the customer | Complaint (late) | Sampling audit with labels |
| Rejects a conforming part (FP) | Unnecessary scrap | High scrap rate | Monitor the rejection rate |
| Silent drift | Progressive degradation | None | PSI + control chart |
| Input outside the domain | Meaningless output | None | Out-of-distribution detection |
| Pipeline failure | No decision / stale decision | System alarm | Heartbeat; defined fallback |
| Wrong labeling on retraining | Model learns the error | None | Labeling audit; agreement |
| Wrong version in production | Unexpected behavior | None | Version check at startup |

**Notice the detection column:** several serious failure modes have "none" for detection in the
usual state. That's exactly where the Action Priority is highest — and where AI FMEA generates
value.

---

## 149.4 Common mistakes

| Mistake | Consequence | Fix |
|---|---|---|
| Treating the model as a tool, not a control | No validation or monitoring | Include it in the control plan |
| No model inventory | Models forgotten in production | A maintained, reviewed inventory |
| Scope of use not documented | Use outside the validated domain | Write down the boundary |
| Automatic retraining without revalidation | An uncontrolled change to a control | Formal revalidation triggers |
| Monitoring only performance | Labels arrive late or never | PSI of the inputs and predictions |
| Nominal human oversight | No one overrides because they lack authority | Explicit authority and logging |
| No fallback plan | Shutdown when the model fails | Define and test the degraded mode |
| Evaluating performance only globally | Bias by line/shift stays invisible | Stratified evaluation |

### Exercises with solutions

**E1 — FMEA of a classification model.**
*Build an FMEA for a model that classifies parts as OK/NOK.*

<details><summary>Solution</summary>

The cell builds the complete FMEA. The four points that set it apart from a conventional process
FMEA:

**1. The failure modes are specific to AI systems.** Beyond classification errors (FN and FP), there
are modes that don't exist in a traditional control: silent drift, input outside the domain, wrong
labeling during retraining, wrong version in production.

**2. Detection is the dominant problem, not occurrence.** Look at the D values: several serious
modes have D ≥ 9 — meaning **there's no detection** in the usual state. A degrading model keeps
producing outputs that look normal. The corrective action isn't to reduce occurrence — it's to
**create the detection**, which means monitoring.

**3. Action Priority differs from RPN.** AP gives severity primacy — with S = 9-10, AP rises as soon
as occurrence or detection stop being the best possible, and the AIAG-VDA reference requires
**management review** of every mode with a safety or regulatory effect, regardless of AP. Sorting by
RPN would put moderate-severity, high-occurrence modes at the top — the wrong priority inversion
when a safety part at the customer is at stake.

**4. The actions are governance actions, not model engineering.** For the dominant modes: PSI
monitoring, sampling audit with labels, version check at startup, out-of-distribution detection,
labeling audit. None of them requires a better model — they require a system built around the model.

**E2 — AI risk register.**
*Build an AI risk register for a failure-prediction system.*

<details><summary>Solution</summary>

Structure, following the taxonomy from section 149.1 and the format from Chapter 143 (each row tied
to an objective, with a named owner):

| Risk (tied to an objective) | Category | Control | KRI |
|---|---|---|---|
| Missing the availability target due to failures the model didn't predict | Model | Temporal validation; baseline vs. scheduled maintenance | Sensitivity in a rolling window |
| Unnecessary maintenance from false positives | Model | Cost-derived threshold (Ch. 138) | Rate of interventions with no finding |
| Degradation after an equipment change | Drift | Revalidation trigger on change | PSI of the inputs |
| Model learns past-maintenance patterns instead of physical degradation | Data | Causal audit of variables; DAG (Ch. 137) | Review of feature importance |
| Loss of decision traceability | Traceability | Log of input, output, version, and threshold | % of decisions with a complete record |
| Dependency: shutdown if the model fails | Continuity | Fallback to a fixed maintenance plan | Semiannual fallback test |

**The two risks specific to this case, and that rarely show up in registers:**

- **Temporal leakage** (Chapter 134): using variables that only exist after the failure (a
  corrective-maintenance work order). Produces an excellent AUC and zero real value.
- **Confounding with the maintenance policy** (Chapter 137): if machines that get more maintenance
  fail less, the model may learn "maintenance causes failure" by reading the correlation backwards.
  It's the same mechanism as a collider.

**Quantification:** for each row, expected loss = P(event) × consequence, using the Chapter 145
structure. Quantification is what lets you compare the cost of controls against the benefit.

</details>

**E3 — Controls by phase.**
*Define controls for input, model, decision, and post-deployment.*

<details><summary>Solution</summary>

**Input (data):**
- Automated data quality profile (Chapter 109): completeness, validity, uniqueness, range.
- Out-of-distribution detection — is the input inside the validated domain?
- Schema verification: columns, types, units. An upstream unit change is one of the most common
  causes of silent failure.
- Labeling audit: inter-rater agreement (kappa), review sampling.

**Model:**
- Version pinned and verified at system startup.
- Validation metrics logged and compared against the acceptance criterion.
- Calibration verified and, if needed, corrected (Chapter 138).
- **Stratified** evaluation by line, shift, and variant — not just global.

**Decision:**
- Threshold derived from the cost of the errors, documented and under change control.
- An indecision zone that routes to human review, instead of forcing a binary decision.
- Complete log: input, output, version, threshold, final decision, and whether it was overridden.
- Defined human authority: who can override, and the record of that decision.

**Post-deployment:**
- PSI of the inputs and predictions, with thresholds and a reaction plan.
- Periodic audit with true labels (a sample of parts reinspected by an independent method) — the
  only way to measure real sensitivity.
- Control chart on the model's rejection rate: SPC applied to the model.
- Revalidation triggers tied to the change control process.
- Periodic review as part of management review.

</details>

**E4 — When to revalidate.**
*Determine when a model change should go through formal revalidation.*

<details><summary>Solution</summary>

The list of triggers is in the cell. The more interesting question isn't *what* the triggers are,
but **how much it costs not to have them** — and the simulation answers that.

With a supplier change in month 12 that degrades sensitivity from 0.94 to 0.68:

| Detection policy | Month detected | Cost of the extra NC |
|---|---|---|
| Trigger on supplier change | 12 | €0 |
| Monthly PSI monitoring | 13 | ~€150k |
| Quarterly audit with labels | 15 | ~€450k |
| Annual revalidation only | 24 | ~€1.8M |
| Relying on customer complaints | 30 | ~€2.7M |

**The governance conclusion, and it's the chapter's most important one:** the most effective control
**is not technical**. The trigger on supplier change detects it in the very same month, costs zero,
and requires no technology at all — it's a line added to the change-control procedure the
organization already has.

Automatic monitoring (PSI) is valuable because it catches what procedural triggers don't anticipate.
But the two are complementary, and the procedural one is cheaper and faster.

**The practical implication:** integrate the **model inventory** with the quality system's **change
control process**. When an engineering, supplier, or process change is approved, the system should
automatically identify which models are affected and require a decision on revalidation. That's
precisely the integration ISO/IEC 42001 expects of an AI management system — and it's what
distinguishes an organization that manages AI from one that merely has models.

</details>
