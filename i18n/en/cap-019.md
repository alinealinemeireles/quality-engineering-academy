## Chapter 19: Standard Work ✦

### The engineering question

*If two people run the same operation and get different times and results, which of the two methods is the process?*

The lean answer is uncomfortable: **neither**. As long as standard work doesn't exist, no process exists — there are two competing variants, and any capability measurement, any Gage R&R, and any DMAIC project is measuring the mixture of the two.

That's why standard work opens the list of lean tools instead of closing it. It's the **statistical prerequisite** for everything that follows. A process with no standard doesn't have separable common-cause and special-cause variation: it just has noise from several overlapping sources.

### The three elements of standard work

The Toyota system defines standard work through three elements, not through a document:

| Element | What it is | Common mistake |
|---|---|---|
| **Takt time** | The pace of customer demand. Defines how long the operation *can* take. | Confusing it with how long the operation *currently* takes. |
| **Work sequence** | The exact order of steps the operator carries out. | Documenting the ideal sequence instead of the actual one. |
| **Standard work-in-process (SWIP)** | The minimum quantity of parts that needs to be at the station for the sequence to repeat without stopping. | Treating it as "safety stock" and inflating it. |

The three form a system. Changing the takt forces a review of the sequence; changing the sequence usually changes the SWIP.

**Documents that support standard work**

- **Process Capacity Sheet** — manual time, machine time, and changeover time per operation, to identify the bottleneck.
- **Standard Work Combination Table** — overlays manual work, machine work, and walking on a timeline; this is where waiting becomes visually apparent.
- **Standard Work Chart** — the station layout with the operator's path, the SWIP location, and the quality checkpoints.

### Standard Work Is Not a Procedure

This confusion is costly in audits and improvement projects:

| | Procedure / Work Instruction | Standard Work |
|---|---|---|
| Who writes it | Engineering / Quality | The team that executes it, with the leader |
| What it's for | Document compliance | A basis for improvement |
| Review frequency | When the requirement changes | Whenever the team improves the method |
| Where it lives | Document system | At the workstation, visible |
| Contains takt and SWIP | Usually not | Mandatorily |

An ISO 9001 system can be perfectly compliant and have no standard work at all. The reverse happens too.

> **No standard, no kaizen.** Taiichi Ohno framed this as an operating principle: improving means moving the standard from A to B. If A doesn't exist, what got done wasn't improvement — it was change.

### Worked example: is the operation balanced?

An assembly cell has 5 operations. Demand is 460 parts per shift and available time is 27,600 seconds per shift (7h40 net). The observed cycle times per operation are below.

The question isn't "what's the total time?" — it's **"which operations don't fit within takt?"**

```py-r
--- python
import numpy as np
import pandas as pd
import matplotlib.pyplot as plt

tempo_disponivel_s = 27600      # segundos líquidos por turno
procura_pecas = 460             # peças por turno

takt = tempo_disponivel_s / procura_pecas
print(f"Takt time = {takt:.1f} s/peça")

ops = pd.DataFrame({
    "Operacao": ["OP10 Preparação", "OP20 Montagem A", "OP30 Montagem B",
                 "OP40 Aperto", "OP50 Inspeção"],
    "Tempo_ciclo_s": [48.0, 71.5, 52.0, 44.0, 63.0],
})
ops["Folga_vs_takt_s"] = takt - ops["Tempo_ciclo_s"]
ops["Situacao"] = np.where(ops["Tempo_ciclo_s"] > takt, "ACIMA DO TAKT", "ok")
print()
print(ops.to_string(index=False))

gargalo = ops.loc[ops["Tempo_ciclo_s"].idxmax()]
print(f"\nGargalo: {gargalo['Operacao']} ({gargalo['Tempo_ciclo_s']:.1f} s)")
print(f"Capacidade real da célula = {tempo_disponivel_s / gargalo['Tempo_ciclo_s']:.0f} peças/turno")
print(f"Défice face à procura = {procura_pecas - tempo_disponivel_s / gargalo['Tempo_ciclo_s']:.0f} peças/turno")

# Eficiência de balanceamento da linha
n = len(ops)
eff = ops["Tempo_ciclo_s"].sum() / (n * ops["Tempo_ciclo_s"].max())
print(f"Eficiência de balanceamento = {eff:.1%}")

fig, ax = plt.subplots(figsize=(8, 4))
cores = ["#a5203a" if t > takt else "#00688f" for t in ops["Tempo_ciclo_s"]]
ax.bar(ops["Operacao"], ops["Tempo_ciclo_s"], color=cores)
ax.axhline(takt, color="black", linestyle="--", linewidth=1.5)
ax.text(-0.4, takt + 1.5, f"Takt = {takt:.1f} s", fontsize=9)
ax.set_ylabel("Tempo de ciclo (s)")
ax.set_title("Gráfico de balanceamento do operador (Yamazumi)")
plt.xticks(rotation=20, ha="right")
plt.tight_layout()
plt.show()
```

```py-r
--- python
%%R
tempo_disponivel_s <- 27600
procura_pecas <- 460
takt <- tempo_disponivel_s / procura_pecas

ops <- data.frame(
  Operacao = c("OP10 Preparacao", "OP20 Montagem A", "OP30 Montagem B",
               "OP40 Aperto", "OP50 Inspecao"),
  Tempo_ciclo_s = c(48.0, 71.5, 52.0, 44.0, 63.0)
)
ops$Folga_vs_takt_s <- takt - ops$Tempo_ciclo_s
ops$Situacao <- ifelse(ops$Tempo_ciclo_s > takt, "ACIMA DO TAKT", "ok")

cat(sprintf("Takt time = %.1f s/peca\n\n", takt))
print(ops)

gargalo <- ops[which.max(ops$Tempo_ciclo_s), ]
cat(sprintf("\nGargalo: %s (%.1f s)\n", gargalo$Operacao, gargalo$Tempo_ciclo_s))
cat(sprintf("Capacidade real = %.0f pecas/turno\n",
            tempo_disponivel_s / gargalo$Tempo_ciclo_s))
cat(sprintf("Eficiencia de balanceamento = %.1f%%\n",
            100 * sum(ops$Tempo_ciclo_s) / (nrow(ops) * max(ops$Tempo_ciclo_s))))
```

**Engineering reading of the result.** Two operations sit above takt, but only one matters: the bottleneck (OP20) sets the capacity for the whole cell. Speeding up OP50 doesn't produce a single extra part. The ~78% balancing efficiency says roughly a fifth of paid operator time is waiting imposed by the cell's design, not a lack of effort from the people working it.

**Excel 365** — the same calculation with `=AVAILABLE_TIME/DEMAND` for the takt and conditional formatting on the times column, with a `>takt` rule.
**Power BI** — suited for daily tracking of shift-by-shift balancing; the takt calculation becomes a DAX measure. It isn't the place to build the Yamazumi chart for a one-off analysis.
**Minitab** — has no dedicated standard-work function; it would only be used to study cycle-time *variation* (I-MR, capability).

### Common mistakes

1. **Using the average of observed times as the standard.** The standard should be a *repeatable* time by a trained operator, not the average of runs that include interruptions. Log the distribution and work near the mode of the clean cycles.
2. **Writing the standard in an office.** A standard written away from the station is document fiction — and operators know it before the auditor does.
3. **Standardizing before stabilizing supply.** If material runs short twice a shift, the standard isn't executable and the team stops taking it seriously.
4. **Freezing the standard.** A standard that hasn't changed in two years is a sign there's no kaizen, not that the process is excellent.
5. **Confusing SWIP with safety stock.** SWIP is the minimum needed for the sequence to run; safety stock covers demand variability. Mixing the two hides flow problems.
