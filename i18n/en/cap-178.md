## Chapter 178: Medallion Architecture: Bronze, Silver, Gold

<h3 id="a-pergunta-de-engenharia">The engineering question</h3>
<p><em>Raw files arrive dirty — blank values disguised as text ("-", "n/a"), categories with inconsistent capitalization, negative quantities from a sign error. The fact and dimension tables from the <a href="#/aula/cap-177">previous chapter</a> assume the data is already clean. Where does the cleaning happen, and how do you organize a pipeline so each refinement stage is separately auditable?</em></p>
<p>Modern data engineering's answer is to organize the pipeline into <strong>layers of increasing quality</strong> — not a single jump from "raw file" to "table ready for analysis," but intermediate stages, each with a clear responsibility. That's what the medallion architecture is.</p>
<h3 id="from-schema-to-pipeline-why-a-star-schema-isn-t-enough-on-its-own">From schema to pipeline: why a star schema isn't enough on its own</h3>
<p>The dimensional modeling from the previous chapter answers "how do I organize data for analysis." It doesn't answer "how does the data arrive clean in the first place." Between the source file (a MES export, a supplier's CSV, an ERP table) and the final star schema there are usually several transformation steps — removing duplicates, fixing types, standardizing categories, joining sources — and each of those steps can fail or introduce a subtle error.</p>
<p>The <strong>medallion architecture</strong> (a term popularized by Databricks around 2019–2020, in the context of the data lakehouse) organizes this journey into three layers named after precious metals, in increasing order of refinement: <strong>bronze</strong>, <strong>silver</strong>, and <strong>gold</strong>.</p>
<h3 id="the-three-layers-bronze-silver-and-gold">The three layers: bronze, silver, and gold</h3>
<ul>
<li><strong>Bronze</strong> — the entry point. Raw data, as close to the source as possible, with no transformation (or the bare minimum, like adding an ingestion date). The goal is to preserve the source: if something goes wrong later, you can always reprocess from bronze without going back to request the data from the source system again.</li>
<li><strong>Silver</strong> — cleaned and validated data. This is where the removal of disguised blank values, category standardization, correcting quantities with the wrong sign, and deduplication happen — the same cleaning operations covered in the data engineering unit. Silver is still close to the original grain (one row per event), but it's already trustworthy.</li>
<li><strong>Gold</strong> — aggregated data, organized for consumption — typically already in the star schema format from the previous chapter, ready for a dashboard, a machine learning model, or a direct analytical query.</li>
</ul>
<p>The bronze → silver → gold progression isn't just a naming convention for folders or schemas — it's a contract: each layer can only depend on the previous one, never the other way around, which makes the pipeline easier to debug (a problem in gold can only come from silver or the aggregation logic, never "flow back" from gold to corrupt silver).</p>
<h3 id="worked-example-a-minimal-bronze-silver-gold-pipeline">Worked example: a minimal bronze → silver → gold pipeline</h3><div class="codetabs"><div class="ct-bar" role="tablist"><button type="button" class="ct-tab on" role="tab" aria-selected="true" id="ct39a25bff-t0">Python</button></div><div class="ct-pane" role="tabpanel" aria-labelledby="ct39a25bff-t0"><div class="codeblock" data-lang="python"><div class="codebar"><span class="lang">Python</span><button class="btn-copy" type="button">Copy</button></div><pre><code class="language-python">import sqlite3
import pandas as pd

con = sqlite3.connect(":memory:")

# ---------- BRONZE: raw data, exactly as it arrived, with typical dirtiness ----------
bronze = pd.DataFrame({
    "id_evento": [1, 2, 3, 4, 5],
    "maquina":   [" M1", "m2", "M1 ", "M3", "m2"],   # inconsistent spacing/casing
    "qtd":       [120, -45, 98, "n/a", 60],           # wrong sign + disguised blank
    "data":      ["2026-08-01"] * 5,
})
bronze.to_sql("bronze_producao", con, index=False, if_exists="replace")
print("BRONZE (raw, as it arrived):")
print(bronze.to_string(index=False))

# ---------- SILVER: cleaned and validated, still one row per event ----------
silver = bronze.copy()
silver["maquina"] = silver["maquina"].str.strip().str.upper()
silver["qtd"] = pd.to_numeric(silver["qtd"], errors="coerce")   # "n/a" -&gt; NaN
n_antes = len(silver)
silver = silver.dropna(subset=["qtd"])
print(f"\nSILVER: {n_antes - len(silver)} row(s) dropped for invalid qtd")
# Note: a negative sign here would be investigated case by case (return? error?) --
# in this example, it's assumed to be a typo and the absolute value is used.
silver["qtd"] = silver["qtd"].abs()
silver.to_sql("silver_producao", con, index=False, if_exists="replace")
print(silver.to_string(index=False))

# ---------- GOLD: aggregated, ready for direct consumption ----------
gold = pd.read_sql_query("""
    SELECT  maquina, data, SUM(qtd) AS qtd_total, COUNT(*) AS n_eventos
    FROM    silver_producao
    GROUP BY maquina, data
    ORDER BY maquina
""", con)
print("\nGOLD (aggregated, ready for a dashboard):")
print(gold.to_string(index=False))
con.close()</code></pre></div></div></div>
<p><strong>Engineering reading.</strong> Notice each layer has a single responsibility: bronze decides nothing, it just preserves; silver decides what counts as a valid value (but keeps the event-level grain); gold decides how to aggregate for a specific business question. If the business rule for "valid quantity" changes tomorrow, only silver needs to be reprocessed — bronze doesn't change, and gold is recomputed from the new silver.</p>
<h3 id="passthrough-views-silver-vs-aggregated-views-gold">Passthrough views (silver) vs. aggregated views (gold)</h3>
<p>In a SQL Server implementation (instead of pandas), the silver layer is often built as <strong>passthrough views</strong> — views that select and clean columns from bronze 1:1, with no aggregation, keeping the same grain. The gold layer uses <strong>aggregated views</strong>, with <code>GROUP BY</code> and aggregate functions, built on top of the silver views. This separation between "cleaning view" and "aggregating view" mirrors exactly the separation of responsibilities from the example above, just expressed in SQL instead of pandas.</p>
<h3 id="metadata-generated-views-the-52-week-rolling-window-case">Metadata-generated views: the 52-week rolling window case</h3>
<p>A more advanced pattern, common in gold layers that need indicators over sliding time windows (for example, "the last 52 weeks" automatically recomputed every week), is <strong>generating views from metadata</strong> instead of writing each view by hand. A script reads a configuration table (which indicator, which window, which aggregation) and programmatically produces the SQL definition for each view — reducing dozens of nearly identical views to a single parameterized template. It's a technique that only pays off once the number of generated views justifies the extra complexity of generating them instead of writing them by hand — but starting from about a dozen variations of the same pattern, the maintenance payoff is considerable.</p>

<h3 id="common-mistakes">Common mistakes</h3><ol>
<li><strong>Mixing cleaning and aggregation in the same layer.</strong> Makes it impossible to separately debug "the data is wrong" from "the aggregation is wrong."</li>
<li><strong>Overwriting bronze with already-transformed data.</strong> You lose the ability to reprocess from scratch if a silver cleaning rule changes, or if an error is found in the gold aggregation logic.</li>
<li><strong>Treating the medallion architecture as a synonym for dimensional modeling.</strong> They're complementary, not the same thing — medallion organizes <em>pipeline refinement stages</em>; dimensional modeling (previous chapter) organizes the <em>table schema</em> of the gold layer.</li>
<li><strong>Creating dozens of near-identical manual views</strong> instead of considering metadata-driven generation once the pattern repeats — maintenance cost grows linearly with the number of hand-copied views.</li>
<li><strong>Applying ambiguous business rules (e.g., negative quantity) automatically without documenting the decision.</strong> A negative value could be a sign error or a legitimate return — the silver layer's choice should be recorded, not hidden inside a silent <code>.abs()</code>.</li>
